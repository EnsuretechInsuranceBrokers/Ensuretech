Run Ensuretech locally

Every component, in the order to start it. Files used: setup.sql (databases), seed.sql (brokers), local.env (all environment), docker-compose.infra.yml (optional infrastructure). All commands are run from the repository root unless a step says otherwise. Each block has a Copy button.

Honest status. The service-by-service steps and every environment value were verified by running the whole stack in a Linux sandbox (native PostgreSQL, Redis, FerretDB, Kafka, no Docker). docker-compose.infra.yml could not be run there, so treat it as a convenience that is untested. Nothing here talks to a real TPA, insurer, SMS gateway or payment gateway; see docs/runtime-dependencies.md.

1. What runs where

You open one thing: the BFF (a Laravel app) on port 8090. It serves the portal and is the only door to everything else. Every core service refuses calls that did not come through it (§7).

identity-serviceDjango8000ensuretech_identityPostgreSQL, RSA keys
organization-serviceSpring Boot8081ensuretech_orgPostgreSQL, Kafka

Events flow over Kafka (employer.events, policy.events, endorsement.events, cd-balance.updates, tpa.events). That is how policy-service learns of employers, billing opens a deposit account for each new policy, and the dashboards fill in. If Kafka is down the screens that need events stay empty.

3. Infrastructure

Option A: Docker (easiest, untested here)

docker compose -f docker-compose.infra.yml up -d
docker compose -f docker-compose.infra.yml ps

This starts PostgreSQL (and runs setup.sql for you, so skip §4's first step), Redis, MongoDB, Kafka and Mailpit (inbox at localhost:8025). The default PostgreSQL superuser password in the compose file is postgres.

Option B: native

Install and start each with your OS package manager, on the default ports: PostgreSQL 5432, Redis 6379, MongoDB 27017, Kafka 9092, SMTP 1025. For Kafka without Docker (download the 3.9.x tarball from kafka.apache.org, then from its folder):

bin/kafka-storage.sh format -t "$(bin/kafka-storage.sh random-uuid)" -c config/kraft/server.properties
bin/kafka-server-start.sh config/kraft/server.properties

Create the Kafka topics now (do this before the read-service projector starts)

for t in employer.events policy.events endorsement.events cd-balance.updates tpa.events; do
  kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic $t --partitions 1 --replication-factor 1
done

(kafka-topics.sh is in Kafka's bin/; with the Docker image use docker compose -f docker-compose.infra.yml exec kafka /opt/kafka/bin/kafka-topics.sh ….) A consumer that starts before its topic exists logs Unknown topic and may not pick the topic up until restarted.

4. Database and keys

4.1 Databases

psql -h localhost -U postgres -f setup.sql

Creates the login role ensuretech (password ensuretech) and eight UTF-8 databases, one per service. Safe to re-run. One database per service is required: each service creates an outbox schema with the same tables.

4.2 Identity signing keys (once)

identity-service signs tokens with a private key; every other component only needs the public half. The keys folder is git-ignored, so each machine creates its own.

mkdir -p services/identity-service/keys
openssl genrsa -out services/identity-service/keys/jwt-private.pem 2048
openssl rsa -in services/identity-service/keys/jwt-private.pem -pubout -out services/identity-service/keys/jwt-public.pem

4.3 Brokers (after organization-service has run once, §6.2)

psql -h localhost -U ensuretech -d ensuretech_org -f seed.sql

No API creates brokers. Without these rows, creating an employer fails with 409 Duplicate or invalid reference.

5. Environment

local.env holds every variable used below. In every terminal you start a component from, at the repository root:

set -a; source local.env; set +a

Spring services take DATABASE_URL as a JDBC URL and Django services as a postgres:// URL, so local.env has one variable per service (ORG_JDBC, IDENTITY_DB, …) and each launch command below maps it. The four *_CLIENT_* values stay empty until §6.1 creates the service accounts.

The secrets in local.env are generated for development. For anything shared or deployed, generate new ones (php -r 'echo bin2hex(random_bytes(32));') and keep them out of git.

6. Start each component

Order matters the first time: identity → organization, policy, billing → engine → integration → read-service → notification → BFF. After that, any order works as long as Kafka, PostgreSQL and identity are up. Use one terminal per component. Keep a Python virtual environment per service (python3.13 -m venv .venv inside each service folder). The Python services are applications, not installable packages, so dependencies are installed with python ../../scripts/install_python_deps.py (add --dev for the test tools).

6.1 identity-service port 8000

Issues and refreshes tokens, and holds users. First start also creates the machine accounts the engine and integration-service use.

cd services/identity-service
python3.13 -m venv .venv && source .venv/bin/activate
python ../../scripts/install_python_deps.py
cd ../..; set -a; source local.env; set +a; cd services/identity-service
DATABASE_URL="$IDENTITY_DB" python manage.py migrate

Create your first users. Roles: BROKER_ADMIN, BROKER_NON_ADMIN, BROKER_SPECIALIZER, EMPLOYER_ADMIN, EMPLOYER_NON_ADMIN. A broker user needs broker_id (a row from seed.sql); an employer user also needs employer_id, which you only know after creating the employer (§8), so create HR users through the portal/API then. Passwords need 10+ characters and must not be common or similar to the email.

DATABASE_URL="$IDENTITY_DB" python manage.py shell -c "
from django.contrib.auth import get_user_model
U = get_user_model()
U.objects.create_user(email='broker@x.test', first_name='Bro', last_name='Admin', password='Str0ng-Pass-123!', role='BROKER_ADMIN', broker_id=1)
U.objects.create_user(email='other@x.test', first_name='Other', last_name='Broker', password='Str0ng-Pass-123!', role='BROKER_ADMIN', broker_id=2)"

Machine accounts (the secret is shown once; copy both lines into local.env):

DATABASE_URL="$IDENTITY_DB" python manage.py service_account create engine
DATABASE_URL="$IDENTITY_DB" python manage.py service_account create integration
# put the printed values into local.env as ENGINE_CLIENT_ID / ENGINE_CLIENT_SECRET and INTEGRATION_CLIENT_ID / INTEGRATION_CLIENT_SECRET,
# then re-run: set -a; source ../../local.env; set +a

Run it:

DATABASE_URL="$IDENTITY_DB" JWT_PRIVATE_KEY_PATH=keys/jwt-private.pem JWT_PUBLIC_KEY_PATH=keys/jwt-public.pem \
  python manage.py runserver 0.0.0.0:8000 --noreload

Check: curl -s -o /dev/null -w "%{http_code}\n" localhost:8000/api/v1/auth/me/ prints 403 (the secret is required, which is correct).

6.2 organization-service port 8081

Employers (with parent/child), branches, per-employer configuration. Publishes employer.events.

cd services/organization-service
mvn -DskipTests package
DATABASE_URL="$ORG_JDBC" PORT=8081 java -jar target/organization-service-0.1.0.jar

Flyway creates the tables on first start. Then do §4.3 (seed.sql). Check: curl -s localhost:8081/actuator/health → "status":"UP".

6.3 policy-service port 8082 · gRPC 9090

Policies, rate cards, family rules, premium rating, contribution/rounding/mid-term settings. The engine calls its gRPC port. Needs Redis.

cd services/policy-service
mvn -DskipTests package
DATABASE_URL="$POLICY_JDBC" PORT=8082 GRPC_PORT=9090 java -jar target/policy-service-0.1.0.jar

6.4 billing-service port 8084 · gRPC 9091

The CD (deposit) ledger: credits, reservations, debits, top-up requests, shared pools. Opens an account automatically when a policy goes live (from policy.events).

cd services/billing-service
mvn -DskipTests package
DATABASE_URL="$BILLING_JDBC" PORT=8084 GRPC_PORT=9091 java -jar target/billing-service-0.1.0.jar

6.5 endorsement engine port 8083

Takes CSV/GUI endorsements through validation, premium calculation, deposit check and execution. Two processes: the web app and the outbox relay.

cd services/endorsement-service
python3.13 -m venv .venv && source .venv/bin/activate
python ../../scripts/install_python_deps.py
pip install uvicorn
cd ../..; set -a; source local.env; set +a; cd services/endorsement-service
export DATABASE_URL="$ENDORSEMENT_DB" SERVICE_CLIENT_ID="$ENGINE_CLIENT_ID" SERVICE_CLIENT_SECRET="$ENGINE_CLIENT_SECRET"
python manage.py genproto          # gRPC stubs (git-ignored, must be generated once)
python manage.py migrate
uvicorn config.asgi:application --host 0.0.0.0 --port 8083

It must run under uvicorn (ASGI), not runserver, or live progress streaming would block a worker. In a second terminal, with the same exports, publish its outbox to Kafka every 2 seconds (stand-in for the Celery beat schedule, since there is no RabbitMQ):

cd services/endorsement-service && source .venv/bin/activate
cd ../..; set -a; source local.env; set +a; cd services/endorsement-service
DATABASE_URL="$ENDORSEMENT_DB" SERVICE_CLIENT_ID="$ENGINE_CLIENT_ID" SERVICE_CLIENT_SECRET="$ENGINE_CLIENT_SECRET" python scripts/relay_loop.py
With RabbitMQ you would instead set CELERY_BROKER_URL, drop CELERY_TASK_ALWAYS_EAGER, and run celery -A config worker and celery -A config beat. Not exercised here.

6.6 integration-service port 8085

TPA connections, push of endorsements to TPAs, reconciliation of TPA rosters. Calls the engine and policy-service. Scheduled reconciliation is off unless RECONCILE_ENABLED=true.

cd services/integration-service
mvn -DskipTests package
DATABASE_URL="$INTEGRATION_JDBC" PORT=8085 SERVICE_CLIENT_ID="$INTEGRATION_CLIENT_ID" SERVICE_CLIENT_SECRET="$INTEGRATION_CLIENT_SECRET" \
  java -jar target/integration-service-0.1.0.jar

It refuses TPA base URLs that are not https or that resolve to private addresses (SSRF guard). For a TPA on your own machine add TPA_ALLOW_HTTP=true TPA_ALLOW_PRIVATE_HOSTS=true, development only.

6.7 read-service port 8087

Dashboards, activity lists, reports and the assistant (knowledge base search; free extractive answers by default). Two processes: the API and the projector that turns Kafka events into read models.

cd services/read-service
python3.13 -m venv .venv && source .venv/bin/activate
python ../../scripts/install_python_deps.py
cd ../..; set -a; source local.env; set +a; cd services/read-service
python manage.py runserver 0.0.0.0:8087 --noreload

Second terminal (same activation and source local.env):

python manage.py run_projector

No MongoDB? Run FerretDB over PostgreSQL instead: create a UTF-8 database ferretdb (see the commented block in setup.sql), run ferretdb --postgresql-url=postgres://ensuretech:ensuretech@localhost:5432/ferretdb --listen-addr=127.0.0.1:27017, and leave MONGO_URI as is. A database not created as UTF-8 makes every read-service call fail with client_encoding is SQL_ASCII.

6.8 notification-service workers · optional

Turns events into emails. Skip it if you do not need mail; nothing else depends on it.

cd services/notification-service
python3.13 -m venv .venv && source .venv/bin/activate
python ../../scripts/install_python_deps.py
cd ../..; set -a; source local.env; set +a; cd services/notification-service
export DATABASE_URL="$NOTIFICATION_DB"
python manage.py migrate
python manage.py run_consumer      # terminal 1: Kafka -> queued emails
python manage.py run_sender        # terminal 2: queued emails -> SMTP (Mailpit shows them on :8025)

The consumer and sender loops are covered by tests with fakes but have not been run against a live broker.

6.9 sheet-generator-service port 8086 · optional

Builds the employee-upload spreadsheet for a policy. The page at / also works offline.

cd services/sheet-generator-service
mvn -DskipTests package
DATABASE_URL="$SHEETGEN_JDBC" PORT=8086 java -jar target/sheet-generator-service-0.1.0.jar
# open http://localhost:8086/     (or just open src/main/resources/static/index.html in a browser: it needs no server)

It is not wired into the portal. The BFF only exposes it when BFF_QA_TOOLS=true.

6.10 BFF and portal port 8090

cd services/bff
composer install
cp .env.example .env
php artisan key:generate

Edit services/bff/.env: set BFF_GATEWAY_SECRET to the same value as GATEWAY_SECRET in local.env, and check the UPSTREAM_* ports (the defaults match this guide). Everything else can stay. Or skip editing and pass them from local.env:

cd ../..; set -a; source local.env; set +a; cd services/bff
PHP_CLI_SERVER_WORKERS=4 php artisan serve --host 0.0.0.0 --port 8090

Open http://localhost:8090/login. PHP_CLI_SERVER_WORKERS=4 matters: a live-progress stream holds one worker while it is open. php artisan serve is for development; put nginx + PHP-FPM in front for anything real.

The BFF also exposes a JSON API under /api/v1/{broker|employer}/… for other frontends; services/bff/README.md lists it.

7. The gateway secret (why a direct call returns 403)

GATEWAY_SECRET in every core service and BFF_GATEWAY_SECRET in the BFF must be the same value. The BFF sends it on every call together with a session key (an HMAC of a session id). A service refuses its browser-facing paths without both, even when the user's token is valid. Check it:

# should print 403 for every one of these (direct to the service, no secret):
for p in 8081/api/v1/broker/employers 8082/api/v1/broker/policies 8084/api/v1/broker/cd/accounts 8085/api/v1/broker/integration/status 8083/api/v1/broker/endorsements/ 8087/api/v1/broker/read/dashboard/; do
  curl -s -o /dev/null -w "$p -> %{http_code}\n" localhost:$p; done

If a service is started without the variable, it still runs but logs GATEWAY_SECRET is not set and does not protect itself. If the BFF and a service have different values, every portal page backed by that service fails with 403/502.

8. First run walkthrough

  1. Open http://localhost:8090/login, sign in as broker@x.test / Str0ng-Pass-123!.
  2. Employers → add one (code ACME). Note its id from the API below (first one is usually 1).
  3. Create the HR user for that employer (replace EMPLOYER_ID). The portal has no user screen; use the API: 
    B=http://localhost:8090/api/v1
TOKEN=$(curl -s $B/auth/login -H 'Content-Type: application/json' -d '{"email":"broker@x.test","password":"Str0ng-Pass-123!"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
curl -s $B/broker/employers -H "Authorization: Bearer $TOKEN"                       # find the employer id
curl -s $B/broker/users -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"hr@acme.test","first_name":"Hr","last_name":"Acme","role":"EMPLOYER_ADMIN","employer_id":EMPLOYER_ID,"password":"Str0ng-Pass-123!"}'
  4. Create and configure a policy (API; the portal shows and approves policies but does not edit their configuration). premium_type_id 1 is FLAT; relation ids 2,5,9 are Spouse, Son, Daughter: 
    H="Authorization: Bearer $TOKEN"; J='Content-Type: application/json'
curl -s $B/broker/policies -H "$H" -H "$J" -d '{"employer_id":EMPLOYER_ID,"policy_number":"POL-001","insurer_id":1,"policy_type":"GMC","premium_type_id":1,"suminsured_subtype_id":1,"rater_type_id":1,"start_date":"2026-04-01","end_date":"2027-03-31","pro_rata_type":"DAILY"}'
# use the returned id as POLICY_ID:
curl -s -X PUT $B/broker/policies/POLICY_ID/rate-card -H "$H" -H "$J" -d '{"effective_from":"2026-04-01","tax_rate":18,"rate_table":{"flat":1000}}'
curl -s -X PUT $B/broker/policies/POLICY_ID/family-construct -H "$H" -H "$J" -d '{"allowed_relations":[2,5,9],"max_members":6,"max_children":2}'
    Then in the portal: Policies → POL-001 → Approve and go live. Within a few seconds CD balance shows an account for it (created from the policy event).
  5. CD balance → record a deposit of 50000 (broker). Sign in as hr@acme.test in a private window to see the employer's view and request a top-up (the broker approves it via the API: POST /api/v1/broker/cd/accounts/POLICY_ID/replenishments/ID/approve).
  6. Endorsements → upload this file (policy POL-001, operation ADD, any effective date inside the policy period): 
    Emp Code,Relationship,Member Name,DOB,Gender,Sum Insured,Effective Date,PAN
1001,Self,Asha Rao,17/05/1985,F,500000,,ABCDE1234F
1001,Spouse,Ravi Rao,02-Feb-1983,M,500000,,
1001,SON,Kid Rao,01/01/2015,M,500000,,
1002,Self,Meera Nair,1990-03-03,F,300000,,PQRST5678K
    The job page shows progress live and ends at ENDORSED; CD balance drops by the premium. With no deposit it stops at CD_INSUFFICIENT; deposit, then press Retry. A file with bad dates/PAN/relations stops at VALIDATION_PARTIAL with a line-by-line list of problems.
  7. Dashboard now shows job and deposit counts (from Kafka → read-service). Assistant answers from knowledge you add: POST /api/v1/broker/assistant/knowledge with {"title":"…","text":"…"}.

9. Tests

Each suite is self-contained (real PostgreSQL for the Spring and engine suites, fake brokers). Run with setup.sql already applied and Redis up. Never run tests against a database you care about: they truncate tables. Python suites need the test tools: python ../../scripts/install_python_deps.py --dev.

10. Troubleshooting

SymptomCause and fix
Creating an employer: 409 Duplicate or invalid referenceNo row in organization.brokers for the broker in your token. Run seed.sql (§4.3).
Creating a policy: Employer not foundpolicy-service has not received the employer event. Kafka must be up and organization-service's relay running; wait a few seconds and retry.
CD balance page empty after approving a policybilling-service did not get policy.events. Check Kafka and billing's log.
Dashboards empty, or Unknown topic in the projector logCreate the topics (§3) and restart run_projector. Also check the engine relay_loop.py is running.
read-service: 500 / 502, client_encoding is SQL_ASCIIThe FerretDB database was not created UTF-8. Drop and recreate it with ENCODING 'UTF8' TEMPLATE template0.
Portal shows 403 or 502 for a sectionGateway secret differs between the BFF and that service, or the service is down. Compare GATEWAY_SECRET values; curl localhost:PORT/actuator/health for Spring services.
Login says too many attemptsRate limit protecting login; wait a minute.
Endorsement stuck at CD_INSUFFICIENTNot enough deposit. Credit the account, then Retry.
Engine: cannot import policy_validation_pb2Run python manage.py genproto (stubs are not committed).
Engine/integration log service token or 401 errors calling policy/billingThe *_CLIENT_ID/SECRET in local.env are empty or stale. Recreate the account (§6.1) or rotate: manage.py service_account rotate engine.
Spring service: Connection refused 5432 / Flyway errorPostgreSQL down, or the database does not exist. Re-run setup.sql.
Spring service fails on gRPC port in usepolicy uses 9090 and billing 9091; make sure two copies are not running.
Killed your own shell with pkill -f nameThe pattern matches your own command line. Stop by port: kill $(lsof -ti:8083).
Real TPA / insurer / SMS / paymentsNot implemented; they need contracts and credentials. See docs/runtime-dependencies.md.

11. Stopping and resetting

# stop a component: Ctrl-C in its terminal, or by port
for p in 8090 8087 8085 8084 8083 8082 8081 8086 8000; do kill $(lsof -ti:$p) 2>/dev/null; done

# wipe all data and start clean (destroys everything)
for d in identity org policy billing endorsement integration sheetgen notification; do dropdb -h localhost -U postgres --if-exists ensuretech_$d; done
psql -h localhost -U postgres -f setup.sql
# also delete the Kafka topics/data and the MongoDB database ensuretech_read, or the read models will be inconsistent with the new database
