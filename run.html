0. For the QA run: read this first

Order for a clean run, about 45 minutes the first time:
  1. Install the tools in §1 and run the "check my laptop" block.
  2. Start the infrastructure (§5): PostgreSQL, Redis, Kafka, MongoDB or FerretDB, Mailpit.
  3. Build the databases with \i setup.sql (§2). Two seconds.
  4. Create the signing keys, then start the services one per terminal (§3 is the table, §8 the commands).
  5. Walk through §10 (the main flow with the seeded data), §11 (the TPA offline upload) and §12 (proof that nobody can reach a core service directly).

Everything runs on your own machine and talks only to localhost. Nothing here sends mail, calls a real TPA or insurer, or needs a paid account; docs/runtime-dependencies.md lists what would.

Already running and want to check it? qa/smoke.sh (60 checks, about 50 s) and node qa/portal-smoke.js automate the sanity run; docs/qa-handbook.md has the manual checklist, how to add automation, and a symptom-to-tool debugging table.

2. The database: does \i setup.sql bring it all up?

Yes. setup.sql creates the login role, the eight databases, every table of every service and all the sample data in one go. Checked here on a throwaway PostgreSQL 16 server: it ran in about 2 seconds from a psql prompt with \i setup.sql, created eight databases, and a second run with the reset switch rebuilt them cleanly.

The command you were trying to remember. There is no insert command involved. In psql, \i FILE means "include (run) this file". Two related ones you will use to look around: \l lists databases, \c NAME connects to one, \dt *.* lists tables. Backslash commands belong to the psql program; they are not SQL, so they only work inside psql (not in a GUI tool such as pgAdmin's query box).

Run it

cd /path/to/Ensuretech                          # the repository root: setup.sql is found by relative path
psql -h localhost -U postgres                   # a superuser session (macOS Homebrew: plain  psql postgres)
postgres=# \i setup.sql                         # builds everything; prints "creating ensuretech_... " eight times, then Done
postgres=# \l                                   # you should now see ensuretech_identity, _org, _policy, _billing, _endorsement, _integration, _sheetgen, _notification
postgres=# \q

The one-line equivalent, with no prompt: psql -h localhost -U postgres -f setup.sql. On Linux with the packaged server you may need sudo -u postgres psql instead (the postgres account has no password until you set one). Windows (native psql, not WSL): open setup.sql, find the line \o /dev/null and change it to \o NUL.

Check that it worked

psql -h localhost -U ensuretech -d ensuretech_org -c "select id, name from organization.brokers"        # 2 brokers
psql -h localhost -U ensuretech -d ensuretech_policy -c "select id, policy_number, status from policy_svc.policies"   # 6 policies, one of them live with TPA 3
psql -h localhost -U ensuretech -d ensuretech_endorsement -c "select policy_id, count(*) from endorsement.endorsement_members group by 1"   # members per policy
# password for the ensuretech role is: ensuretech

Rules it follows

  • Run it as a superuser. As an ordinary role it stops at the first line with permission denied to create database.
  • Run it once on a fresh server. A second run stops with database "ensuretech_identity" already exists. That is deliberate: it never overwrites data by accident.
  • To start over (destroys all ensuretech_* data): postgres=# \set reset 1 then \i setup.sql; or psql -h localhost -U postgres -v reset=1 -f setup.sql.
  • Databases only, no tables or data (each service then builds its own tables when first started): \set databases_only 1 then \i setup.sql. Then see §6.3 for the two brokers and §8.1 to create users.
  • Some tables arrive on first start, not from the file. The TPA offline-upload tables (integration-service migration V4) and four new columns on the engine's members table (engine migration 0006) are newer than the file; the services create them themselves (Flyway at start; python manage.py migrate in §8.5). They start empty. This is expected.
  • The seeded data is made up: two brokers, five employers, six policies in different states, 45 members, deposits, endorsement jobs, TPA settings. Nothing in it is real.

A separate test database, next to the one you keep

The databases are named ensuretech_* and the tests erase tables, so do not run the test suites or experiments against a database holding data you want. The clean way to have a disposable copy is a second PostgreSQL server on another port and one variable:

# Docker: a second server on 5433 that builds itself from setup.sql on first start
docker run -d --name ensuretech-test-pg -p 127.0.0.1:5433:5432 -e POSTGRES_PASSWORD=postgres \
  -v "$PWD/setup.sql:/docker-entrypoint-initdb.d/10-setup.sql:ro" postgres:16
# no Docker, Ubuntu:   sudo pg_createcluster 16 qa -p 5433 && sudo pg_ctlcluster 16 qa start
#                      sudo -u postgres psql -p 5433 -f setup.sql
# then, in every terminal that should use the TEST database:
export DB_PORT=5433; set -a; source local.env; set +a        # local.env builds every database URL from DB_PORT
# throw it away and rebuild whenever you like:
docker rm -f ensuretech-test-pg

Everything else (Kafka topics, Redis, MongoDB) is shared, so for a fully separate run also use a second Kafka topic prefix or clear the topics (§15).

3a. One command: the tmux launcher

You do not have to open ten terminals by hand. scripts/dev-up.sh checks your laptop, the infrastructure and the databases, prepares everything the first time (virtual environments, Maven builds when sources are newer than the jar, migrations, the gRPC stubs, the BFF's dependencies and .env, the five Kafka topics), then starts every process in its own tmux window in the right order, waits for identity, and opens a status window showing each port go green.

scripts/dev-up.sh --check          # only check: tools, PostgreSQL/Redis/Kafka/Mongo, databases, keys, secrets. Starts nothing.
scripts/dev-up.sh                  # start everything that can run, then attach to tmux
scripts/dev-up.sh --no-kafka       # Kafka is not running: portal works, but no cross-service events (dashboards, policy-to-billing hand-offs)
scripts/dev-up.sh --with-mail --with-sheet      # also the notification workers and the sheet generator
scripts/dev-up.sh --skip read,projector         # leave components out   (identity org policy billing engine worker-ingest worker-validation worker-computation beat flower integration read projector bff ...)
scripts/dev-up.sh --devtools --ray              # debugging tools (section 16)
DB_PORT=5433 scripts/dev-up.sh     # against the second, throwaway PostgreSQL (section 2)
scripts/dev-down.sh                # stop everything it started (leaves PostgreSQL, Kafka, Redis, Mongo and your data alone)

In tmux: Ctrl-b w lists the windows (identity, org, policy, billing, engine, worker-ingest, worker-validation, worker-computation, beat, flower, integration, read, projector, bff), Ctrl-b n/p moves between them, the mouse works, Ctrl-b d detaches and leaves everything running (tmux attach -t ensuretech comes back). Every window also writes .dev/logs/NAME.log. If a process exits, its window stays open with the reason. Infrastructure is not started by the script: start PostgreSQL, Redis, Kafka and MongoDB first (§5).

What was and was not tested. I ran the script's first-run path in a Linux sandbox without Kafka or MongoDB: tool/infra/database checks, venv creation, dependency install, migrations, stale-jar rebuild, tmux windows and the status page, with --no-kafka. The Kafka-topic step, the read-service and projector windows, --with-mail, and macOS were not run. The first start of a Spring service takes 10-30 s after its window opens.

5. Infrastructure

Option A: Docker (easiest, untested here)

docker compose -f docker-compose.infra.yml up -d
docker compose -f docker-compose.infra.yml ps

This starts PostgreSQL (and runs setup.sql for you, so skip §6.1), Redis, MongoDB, Kafka and Mailpit (inbox at localhost:8025). The default PostgreSQL superuser password in the compose file is postgres.

Option B: native

Install and start each with your OS package manager, on the default ports: PostgreSQL 5432, Redis 6379, MongoDB 27017, Kafka 9092, SMTP 1025. For Kafka without Docker (download the 3.9.x tarball from kafka.apache.org, then from its folder):

bin/kafka-storage.sh format -t "$(bin/kafka-storage.sh random-uuid)" -c config/kraft/server.properties
bin/kafka-server-start.sh config/kraft/server.properties

Create the Kafka topics now (do this before the read-service projector starts)

for t in employer.events policy.events endorsement.events cd-balance.updates tpa.events; do
  kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic $t --partitions 1 --replication-factor 1
done

(kafka-topics.sh is in Kafka's bin/; with the Docker image use docker compose -f docker-compose.infra.yml exec kafka /opt/kafka/bin/kafka-topics.sh ….) A consumer that starts before its topic exists logs Unknown topic and may not pick the topic up until restarted.

6. Database and keys

6.1 Databases

psql -h localhost -U postgres -f setup.sql

One file builds everything: the login role ensuretech (password ensuretech), the eight UTF-8 databases (one per service, which is required: each service creates an outbox schema with the same tables), every table of every service, and a story's worth of sample data in all of them (two brokers, five employers, five policies, deposits, a dozen endorsement jobs, TPA settings, mail logs). The services find their tables already there and start without migrating. The sample users, their shared password and the engine's service account are listed in the file's header comment. It stops at the first error; to start over use psql -h localhost -U postgres -v reset=1 -f setup.sql, which drops the ensuretech_* databases first. Want empty databases that each service fills itself? -v databases_only=1. Not in the file: read-service's MongoDB data, which is built from Kafka events as new work happens.

6.2 Identity signing keys (once)

identity-service signs tokens with a private key; every other component only needs the public half. The keys folder is git-ignored, so each machine creates its own.

mkdir -p services/identity-service/keys
openssl genrsa -out services/identity-service/keys/jwt-private.pem 2048
openssl rsa -in services/identity-service/keys/jwt-private.pem -pubout -out services/identity-service/keys/jwt-public.pem

6.3 Brokers

Already in setup.sql (Northwind Brokers and Southbridge). If you built empty databases with databases_only=1, run psql -h localhost -U ensuretech -d ensuretech_org -f seed.sql after organization-service has started once. No API creates brokers; without these rows, creating an employer fails with 409 Duplicate or invalid reference.

7. Environment

local.env holds every variable used below. In every terminal you start a component from, at the repository root:

8. Start each component

Order matters the first time: identity → organization, policy, billing → engine → integration → read-service → notification → BFF. After that, any order works as long as Kafka, PostgreSQL and identity are up. Use one terminal per component. Keep a Python virtual environment per service (python3.13 -m venv .venv inside each service folder). The Python services are applications, not installable packages, so dependencies are installed with python ../../scripts/install_python_deps.py (add --dev for the test tools).

8.5 endorsement engine port 8083

Takes CSV/GUI endorsements through validation, premium calculation, deposit check and execution. The web app, plus the Celery workers, beat and Flower below.

cd services/endorsement-service
python3.13 -m venv .venv && source .venv/bin/activate
python ../../scripts/install_python_deps.py
pip install uvicorn
cd ../..; set -a; source local.env; set +a; cd services/endorsement-service
export DATABASE_URL="$ENDORSEMENT_DB" SERVICE_CLIENT_ID="$ENGINE_CLIENT_ID" SERVICE_CLIENT_SECRET="$ENGINE_CLIENT_SECRET"
python manage.py genproto          # gRPC stubs (git-ignored, must be generated once)
python manage.py migrate
uvicorn config.asgi:application --host 127.0.0.1 --port 8083

It must run under uvicorn (ASGI), not runserver, or live progress streaming would block a worker. The pipeline itself (ingest the file, validate chunks, price chunks, check the deposit, apply chunks) is Celery: the web process only queues tasks, workers do them. Start these in their own terminals, each with the same exports as above (source local.env, DATABASE_URL, SERVICE_CLIENT_ID/SECRET), from services/endorsement-service with the virtual environment active:

celery -A config worker -n ingest@%h     -Q csv.ingestion,gui.batch,maintenance        -c 2 -l info
celery -A config worker -n validation@%h -Q validation.high,validation.standard         -c 2 -l info
celery -A config worker -n computation@%h -Q computation                                -c 2 -l info
celery -A config beat -l info -s ../../.dev/celerybeat-schedule        # the schedule: outbox to Kafka every 5 s, expire GUI sessions every 5 min
celery -A config flower --address=127.0.0.1 --port=5555 --basic-auth="$FLOWER_BASIC_AUTH"     # the dashboard

Broker. CELERY_BROKER_URL in local.env defaults to Redis (redis://localhost:6379/1), which is already running for policy-service. The engine is designed for RabbitMQ (amqp://guest:guest@localhost:5672//): its six queues carry priorities and dead-letter queues, which are RabbitMQ features. On Redis the pipeline runs but there are no dead-letter queues. docker compose -f docker-compose.infra.yml up -d rabbitmq starts RabbitMQ (management page localhost:15672, guest/guest); scripts/dev-up.sh uses it automatically when it answers on 5672. Without Kafka, set RELAY_OUTBOX=false (the script does with --no-kafka) so beat does not try to publish.

Flower (127.0.0.1:5555, login in local.env FLOWER_BASIC_AUTH) shows each worker and the queues it serves, every task with its arguments, state, runtime, retries and which worker took it, and lets you revoke or retry. Upload an endorsement and watch: ingest_csv on the ingest worker, validate_chunk on validation, then start_premium_calculation, price_chunk, check_cd_balance and apply_chunk on computation. Flower can revoke tasks and stop workers: keep it on 127.0.0.1 behind its login, never on a public address.

CELERY_TASK_ALWAYS_EAGER=true still exists as a shortcut that runs every task inline inside the web process (no workers, no broker, no Flower; scripts/dev-up.sh --eager). Use it only to debug a single task in a debugger; it hides exactly what Celery is for (parallel chunks, retries, queue isolation).

9. The lock on the core services

Nobody can curl or use Postman against a core service, with a stolen token or without one. Each core service refuses every request unless it carries the BFF's signature (or a SYSTEM token, below). The BFF signs every call it makes with BFF_GATEWAY_SECRET: a timestamp, a one-time nonce, and an HMAC over the method, path, query and a hash of the user's token. A signature works for one request, for 60 seconds, and the secret itself is never sent. Details: docs/core-lockdown.md.

  • GATEWAY_SECRET (every core service) and BFF_GATEWAY_SECRET (BFF) must be the same value; local.env sets both. A core service refuses to start without it (GATEWAY_SECRET is not set), so a forgotten source local.env shows up immediately.
  • Clock: the 60-second window means the machines must agree on the time. On one laptop that is automatic.
  • Super credentials: the one other way in is a SYSTEM token: a service account (client id plus a long secret, stored hashed in identity) signs in at /api/v1/auth/service-token/. The engine and integration-service do this automatically; an operator can do it by hand (§12). It reaches the internal endpoints, not the broker or employer screens.
  • Only /actuator/health (Spring) and that service-token sign-in are open to everyone.

§12 has the commands that prove all of this on your machine.

JobRunr / Quartz: the sync queue is already a database-backed job system (leases, retries, dead-letter), so a second one would duplicate it; the controls are built on it instead (rationale in docs/observability.md). Laravel Horizon watches Redis queues, and the BFF has no queued jobs (every job would run inline), so its dashboard would always be empty. Distributed tracing (OpenTelemetry/Jaeger) is not wired. Each becomes useful when the thing it watches exists; ask and I will add it then.
